<objective>
Create the device-token persistence layer and authenticated registration API. A client can register a device push token (upserted by `(userId, deviceId)`) and unregister a device on logout, with multiple active devices per user supported. Establishes the `com.catspell.api.push` module (`model` / `service` / `controller`) mirroring existing domain modules, plus the Flyway V14 migration, JPA entity, repository, request DTO, transactional service, and integration tests.

Implements decisions D-01 (device API contract under /api/devices), D-02 (upsert key (userId, deviceId)), D-03 (platform enum ANDROID/IOS only), D-04 (soft-deactivate on unregister), and D-05 (active-row filtering + re-activation on re-register).
</objective>

<must_haves>
- Flyway `V14__create_device_tokens_table.sql` creates `device_tokens` with a UNIQUE `(user_id, device_id)` constraint (the upsert key, D-02).
- `POST /api/devices` upserts by `(userId, deviceId)`: re-registering the same device updates the token and re-activates the row (`active=true`, `deactivated_at=null`) (D-05).
- `DELETE /api/devices/{deviceId}` soft-deactivates (`active=false` + `deactivatedAt` set), never hard-deletes (D-04), and affects only the caller's named device.
- Multiple active devices per user are supported (PUSH-02).
- userId is taken from `SecurityContextHolder` (never from the request body) — a user can only mutate their own tokens.
- `platform` enum is `ANDROID` / `IOS` only — no `WEB` (D-03).
- Both endpoints require authentication (not in the `permitAll` list).
- Entity matches the migration exactly (ddl-auto is `validate`).

truths:
  - "D-01: REST endpoints under /api/devices — POST registers/upserts (token, deviceId, platform); DELETE /api/devices/{deviceId} unregisters"
  - "D-02: Upsert key is (userId, deviceId) — client-supplied deviceId identifies the device"
  - "D-03: platform enum scoped to ANDROID / IOS only (no WEB)"
  - "D-04: Soft-deactivate on unregister — active=false + deactivatedAt timestamp, no hard-delete"
  - "D-05: Send/query paths filter WHERE active = true; re-registering same (userId, deviceId) re-activates via upsert"
  - "PUSH-01: Register device token via authenticated endpoint, upserted by (user_id, device_id)"
  - "PUSH-02: Unregister on logout; multiple active devices per user supported"

prohibitions:
  - statement: "userId MUST NOT be read from the request body or path — always from SecurityContextHolder"
    status: resolved
    verification: "DeviceController extracts userId via SecurityContextHolder; request DTO has no userId field"
  - statement: "Tokens MUST NOT be hard-deleted on unregister"
    status: resolved
    verification: "DELETE path sets active=false; no repository delete call in unregister"
</must_haves>

<threat_model>
ASVS L1 — block on: high.

- **T-08-01 (IDOR / broken object-level authz, HIGH — mitigated):** A caller could attempt to register or delete tokens belonging to another user by supplying a foreign userId or deleting a device they don't own. **Mitigation:** userId is always derived from `SecurityContextHolder.getContext().authentication.principal` (identical to `ConversationController.extractUserId()`); the request DTO carries no userId; `DELETE` scopes the update to rows matching `(callerUserId, deviceId)`, so a caller can never affect another user's device. Verified by an integration test that registers a device as user A and confirms user B's DELETE of that deviceId does not deactivate A's row.
- **T-08-02 (sensitive data at rest, LOW — accepted):** FCM registration tokens are stored in plaintext. These are delivery-routing identifiers, not credentials granting access, and are scoped per user with `ON DELETE CASCADE`. No encryption required for L1; acceptable.
- **Auth requirement:** `/api/devices/**` is NOT added to the `permitAll` matchers in `SecurityConfig`, so it falls under `anyRequest().authenticated()`. Unauthenticated calls return 401.
</threat_model>
