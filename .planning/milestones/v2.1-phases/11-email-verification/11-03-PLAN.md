<objective>
Build the verification business logic and the login hard-gate. `EmailVerificationService` is the
enumeration-safe issue/resend flow (VERIFY-04, D-04/D-05) with a per-email Bucket4j guard that issues
a hashed, 24-hour (D-08) single-use token and sends it via the Plan 02 renderer + existing EmailSender.
`AuthService.verifyEmail` claims the token atomically and stamps `email_verified_at` with NO session
(VERIFY-02, D-02); `AuthService.login` gains the `EMAIL_NOT_VERIFIED` 403 gate after the password
check (VERIFY-03, D-03). Both new public endpoints are added to the three security whitelists.

Purpose: Provide the service + gate that Plan 04's controller and register wiring depend on.
Output: `EmailVerificationService.kt`, `verifyEmail` + login-gate in `AuthService.kt`,
`EmailNotVerifiedException` + its 403 handler, and the three whitelist edits.

Note: This plan intentionally does NOT modify `register` — the register no-token contract change is
colocated with its controller change in Plan 04 so the codebase compiles at the end of each plan.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → HTTP API | Untrusted email/token inputs reach the service; responses must not leak account state. |
| service → DB | Token lookups and single-use claims cross into persistence; must be atomic + parameterized. |
| auth decision | The login gate decides session issuance based on verified state. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-09 | Information Disclosure | Account/verification-status enumeration via resend | high | mitigate | resend returns normally for unknown/verified/rate-limited emails; no distinct status/body/429 (Task 1, D-04) — prohibition authored. |
| T-11-10 | Information Disclosure | Enumeration via login gate ordering | high | mitigate | Gate evaluated AFTER password check; unknown email + wrong password both stay generic 401 (Task 2, D-03). |
| T-11-11 | Tampering | Verification-token replay/reuse (double verify) | high | mitigate | Atomic markUsed conditional UPDATE; second concurrent/repeat claim matches zero rows → InvalidTokenException (Task 2, VERIFY-02). |
| T-11-12 | Elevation of Privilege | Session minted from a link token (verify auto-login) | high | mitigate | verifyEmail returns no tokens and never calls revokeAllUserTokens; user must log in fresh (Task 2, D-02) — prohibition authored. |
| T-11-13 | Denial of Service | Email-bombing a specific address via resend | high | mitigate | Per-email Bucket4j guard (Task 1) + per-IP AUTH_PATHS layer (Task 3), two-layer per D-05. |
| T-11-14 | Spoofing | IDOR: token→user binding bypass | medium | mitigate | Token row carries the user_id FK; verifyEmail resolves the user from the claimed token only, never from client input (Task 2). |

| T-11-SC | Tampering | npm/pip/cargo installs | high | accept | No new dependencies this phase — nothing to audit. |
