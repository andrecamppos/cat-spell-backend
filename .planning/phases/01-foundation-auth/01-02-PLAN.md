<objective>
Refresh Token Rotation: Add rotating refresh tokens stored in PostgreSQL with theft detection and multi-device support. After this plan, a user can refresh their expired access token — the last piece of the JWT auth lifecycle.

Purpose: Complete the JWT token lifecycle (AUTH-03). Without refresh tokens, users must re-login every hour (access token expiry). Rotation with theft detection prevents token replay attacks.

Output: RefreshToken entity, V2 migration, refresh endpoint, token rotation logic, theft detection, integration tests.

Decisions implemented: D-06 (rotating refresh tokens in DB, theft detection via reuse), D-07 (30-day refresh token expiry), D-08 (multi-device sessions with independent refresh tokens).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → /api/auth/refresh | Refresh token transmitted from client storage to server |
| Refresh token storage (client) | Token persisted on device, vulnerable to device compromise |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-08 | Spoofing | /api/auth/refresh | mitigate | Token rotation: each refresh invalidates old token, preventing replay; theft detection revokes all tokens on reuse of revoked token (D-06) |
| T-01-09 | Tampering | refresh_tokens table | mitigate | Token is opaque UUID (not JWT), server-side validation; FK constraint with ON DELETE CASCADE ensures cleanup |
| T-01-10 | Information Disclosure | Refresh token in response | accept | Token transmitted over HTTPS (enforced at deployment level); stored securely on client (mobile app responsibility) |
| T-01-11 | Denial of Service | Token family revocation | accept | Theft detection revokes all user tokens; legitimate user must re-login; acceptable tradeoff for security |
</threat_model>
