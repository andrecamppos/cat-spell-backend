<objective>
Close first-review WR-05 and WR-06 (D-10, "flush, send, roll back"):
- **WR-05:** the invite email is sent before the invite row is flushed, and a row lock is held across unbounded external I/O.
- **WR-06:** delivery failures are swallowed with no cause and no log.

After this plan:
- InviteService flushes the row first.
- The render happens outside the error mapping, so renderer bugs surface as 500s.
- The send runs on a small private executor and is awaited with a strict timeout. It stays synchronous inside the transaction, so a failure still rolls back INVITED and the invite and returns the existing retryable 502.
- Every failure logs one address-free WARN and chains its cause.

Deviation from RESEARCH Pattern 4 step 6, found during planning: RESEARCH proposed a `ThreadPoolTaskExecutor` bean. Spring Boot 4.0.6 creates `applicationTaskExecutor` only `@ConditionalOnMissingBean(Executor.class)`. A new Executor bean would therefore remove the auto-configured executor, and `@Async` (push, email, report and WebSocket reconnect listeners) would fall back to the tiny invite pool. The executor is a private field instead, shut down with `@PreDestroy`.

Recorded residual (RESEARCH Pattern 4 point 8; documented in 18-11): `future.cancel(true)` interrupts the worker, but a provider that ignores interrupts may still deliver a code that was rolled back. Redeeming that code fails with the generic invite-required 403, and the operator's retry sends a valid code. The row lock and pooled connection are held for at most the timeout.

Spec-less probe fallback skipped: the phase has no requirement IDs to probe (visible skip).

Git: **stage only, never commit**. Stage this plan's paths explicitly with `git add <path>`.
</objective>
