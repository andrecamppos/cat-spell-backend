<objective>
Build the invite domain service and its error contract: the single generic invite exception + admin-auth exception with their RFC 7807 mappings, the issuance DTOs, and `InviteService` with `create`/`validate`/`consume`. This reuses the in-repo hashed-single-use-token discipline verbatim (SecureRandom generator, SHA-256 hash-at-rest, atomic conditional-UPDATE claim) and writes referral attribution only when a real referrer exists.

Purpose: This is the security core of the phase. It enforces high-entropy hashed single-use codes (INV-04), enumeration-safe indistinguishable failures (INV-04/D-10), referral integrity (INV-05/D-11/D-12), and the programmatic issuance path (INV-02/D-06) that Phase 17 will reuse.
Output: `InviteRequiredException`/`AdminAuthException` + handler mappings, `IssueInviteRequest`/`IssueInviteResponse`, `InviteService`, and integration tests for single-use + referral attribution.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → InviteService | Untrusted invite codes and referrer ids enter validate/create; the service is the authority that hashes, looks up, and claims. |
| InviteService → PostgreSQL | The atomic conditional UPDATE claim is where single-use is truly enforced (under a DB row lock). |
| InviteService → GlobalExceptionHandler | All failure modes converge on one exception → one 403 body (no enumeration channel). |

| T-16-06 | Information Disclosure | InviteService.validate failure modes | high | mitigate | Null/blank/not-found/consumed all throw the SAME `InviteRequiredException` → one 403 body + `code=INVITE_REQUIRED`; invalid == consumed == missing (D-10, INV-04). |
